# AI Pilot 双仓库同步设计

## 目标

独立 AI Pilot 仓库维护在个人 GitHub；团队继续在 Giant-Panda-AI-Tools 的
`mcp/ai-pilot` 目录开发。用户已确认团队改动允许回传个人仓库。同步由维护者
操作，其他同事不需要独立仓库或 subtree 命令。

## 选择

用 `git subtree split` 提取团队目录，保留目录相关提交；在独立仓库的隔离
副本中通过 Git 合并。导出时在团队隔离副本执行 subtree rejoin/merge，保持
团队目录之外的文件和历史。放弃 rsync 覆盖与自动推送。

第一次通过明确的独立仓库/团队仓库历史基线建立共同祖先。两个基线不完全
相同的文件需审核合并，不将任一副本强行覆盖为另一副本。后续使用已建立
的 ancestry 进行正常合并。所有来源 SHA、提取 SHA、结果 SHA 和方向写入
本次操作的 JSON 记录。

## 工具

- `status`：只读显示双方提交、工作区是否干净、路径和树差异。
- `import`：在临时 clone 中提取团队目录、合并到独立仓库的新分支。
- `bootstrap`：先连接指定的历史基线，再合并独立仓库当前提交和团队当前提取。
- `export`：在临时团队 clone 中 rejoin，并把独立仓库提交合入团队目录。
- `continue`：使用上次操作记录，确认冲突已解决并完成剩余合并步骤。
- 每个修改操作必须显式 `--apply`；默认仅输出预览。结果留在隔离副本，
  维护者审核后以分支/PR 合入目标仓库。脚本不自动推送到任何远端。

来源必须是提交：默认 HEAD，可指定 ref；检测未提交代码时拒绝正式操作，
避免误以为未提交功能已同步。个人 .mcp.json、截图、生成目录和 runtime
状态不会通过文件复制进入结果。工作区变化不被 stash、reset 或覆盖。
已被 Git 跟踪的配置仍会参加合并；提交和对外发布前必须审核这些内容。
冲突恢复校验冲突前的提交和双方来源祖先，拒绝中止合并后替换历史的副本。

对外推送前更新目标分支、合并并测试；冲突通过普通 Git 解决。同步结果
表示固定来源 SHA，不承诺两个独立仓库在所有提交时刻实时一致。可在发布
前用 `status --require-equal` 检查目录树一致性，作为 CI/发布门禁。
同步 PR 必须保留合并历史；squash/cherry-pick 会丢失后续合并所需祖先。

## Skill

唯一正文是 AI Pilot 的 `skills/specflow`。团队顶层 `skills/specflow` 可用
相对链接指向 `../mcp/ai-pilot/skills/specflow`，由现有团队安装器发布。仅在
团队审核确认新正文适用于其平台分支后切换，旧正文先保留在 Git 历史。

## 验证

使用临时 Git 仓库验证：首次共同祖先、团队增量导入、个人增量导出、
同文件冲突停留与继续、团队目录外数据保留、脏工作区拒绝、显式预览不
写入仓库、不自动推送、相同版本无变化。现有两个真实仓库先执行只读检查。
