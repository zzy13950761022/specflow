# AI Pilot 开发全程纪实:从想法到可运行

姊妹篇是 `docs/LEARN-TYPESCRIPT.md`(讲语法)。**这一篇讲"为什么"**——我们怎么从一个
模糊需求,一步步做出决策、踩坑、修复,最终得到可运行的 Phase 1。如果你想把这个项目变成
自己的,理解这些**决策和权衡**比记住语法重要得多。

---

## 第 0 幕:需求是怎么被澄清的

最初的输入是一句话:"把三阶段 spec 工作流改造成 8 阶段(SPEC→REQUIREMENTS→DESIGN→
DEVELOP→TEST→BUILD→DEPLOY→OPS)",外加一份别人写的初版方案文档。

**关键教训 1:不要拿到方案就动手。** 我们先做了几件事:
1. 读那份初版方案,发现它其实主张**从零新建一个项目**,而不是改造现有的 `spec-workflow-mcp`。
   这和"改造"二字矛盾——先把这个矛盾摆出来问清楚。
2. 用一连串选择题逐个敲定**不可逆的大决策**(下面详述),而不是边写边改。

**澄清出来的 6 个锁定决策**(这些决定了后面所有代码):
1. 新建项目,但技术栈沿用 Fastify + React + Vite(不自己手写 http)。
2. 8 个阶段挂在 **spec(一个 ticket)** 上,不是挂在每个子任务上。
3. DEVELOP 的子任务 v1 只留数据结构占位,不实现逻辑。
4. v1 只做"薄的垂直切片":只有 SPEC、REQUIREMENTS 两个阶段接真实 Claude 自动化,
   其余 6 个阶段在看板上存在、但 AI 动作是 stub。
5. 不兼容任何存量用户、不发 npm、不要 i18n / VSCode 扩展等历史包袱。
6. (后来追加)prompt 模板必须**按仓库**解析,因为团队有多个框架不同的仓库。

> 为什么"8 阶段挂 spec 还是挂 task"这个问题这么重要?因为它**定义整个数据模型**。
> 挂错了,后面所有代码都得推倒。花十分钟问清楚,省后面十小时返工。

## 第 1 幕:架构的核心比喻 —— 一个大脑,两张嘴

最重要的架构决定:**一个共享领域核心 + 两个薄 transport**。

```
Claude Code  ──(MCP, stdio)──┐
                             ├──▶  AppCore(唯一大脑)──▶ 磁盘文件(唯一事实源)
浏览器里的人 ─(HTTP + WS)───┘
```

- "大脑"是 `AppCore`:所有业务规则只在这里实现一次。
- "两张嘴"是 MCP server 和 Dashboard server:它们**只做翻译**,把外部请求转成对 AppCore
  的调用,不含任何业务逻辑。

**为什么这样分?** 因为同一个操作(比如"批准某阶段")可能从 Claude 来、也可能从浏览器来。
如果规则写在两处,迟早不一致。把规则收口到 AppCore,两张嘴行为必然一致。

从这个比喻直接推出两条贯穿全项目的**不变量(invariant)**:

- **不变量 #1 —— MCP 的 stdout 只能是 JSON-RPC。** MCP 协议用 stdout 传协议帧,
  你要是往 stdout 打一行日志,就污染了协议、Claude 直接崩。所以**所有日志走 stderr**。
- **不变量 #2 —— 磁盘文件是唯一事实源。** `~/.specflow/registry.json` 只是"加了哪些仓库"
  的索引,随时可丢。真正的状态都在各仓库的 `.specflow/` 里。任何变更必须
  `改内存 → 写盘 → 发事件 → 推给浏览器`,保证浏览器永远和磁盘一致。

## 第 2 幕:构建顺序 —— 由内向外,先测核心

我们没有从"能跑的界面"开始,而是**从最里面的纯逻辑开始,一层层往外包**:

```
1. 脚手架 + logger(先立下不变量 #1)
2. schemas(数据形状)
3. StageMachine(纯状态机)   ← 先写测试!
4. SpecStore(存储)          ← 先写测试!
5. RepoRegistry(索引)
6. AppCore(编排,把 2-5 串起来)
7. MCP server(第一张嘴)     ← 集成测试
8. Dashboard server(第二张嘴)
9. 前端 React 看板
10. stdout 纯净性测试(守不变量 #1)
11. e2e 全链路测试
```

**为什么由内向外?** 因为门控规则(gating)是整个产品的灵魂。我们要在**任何界面存在之前**,
就用单元测试把"没批准不能推进"这条规则钉死。界面是最不稳定的,核心逻辑是最该先稳的。

**为什么先写测试(TDD)?** 以 StageMachine 为例,我们先写了一张"门控真值表"测试:
gate 处于 not_ready / pending_review / rejected 时 advance 都应抛错,只有 approved 才放行。
测试先红,再写实现让它变绿。这样"核心保证"从第一天就有自动化守护,后面任何改动一旦破坏它,
测试立刻报警。

## 第 3 幕:每个核心文件背后的"为什么"

### schemas.ts —— 为什么用 zod 而不是裸 interface
TS 类型编译后被抹掉,运行时读进来的 JSON 没人校验。zod 让"同一份定义"**既是编译期类型、
又是运行期校验器**。读文件时 `.parse()` 一跑,坏数据当场失败,而不是带着脏数据跑到很后面
才诡异崩溃。这是"**让错误尽早、就近爆发**"的工程原则。

### StageMachine —— 为什么是纯函数(无 I/O)
纯函数 `(SpecFile) => SpecFile` 的好处是**可以在内存里毫秒级测完所有分支**,不碰文件系统。
而且它逼我们把"算什么"和"存哪里"彻底分开:算在 StageMachine,存在 SpecStore,编排在 AppCore。
这种分离让每一块都能独立测试、独立替换。

### SpecStore —— 为什么要原子写 + 互斥锁
两个进程(Claude 的 MCP 进程、人的 dashboard 进程)可能**同时写同一个 spec 文件**。
- **原子写**(临时文件 + rename)保证读者不会读到写一半的残文件。
- **per-ticket 互斥锁**(用 Promise 链串行化)保证同一 ticket 的多次写不会交错。
这两个机制是"多进程共享文件"场景的标配,不是过度设计。

### AppCore —— 为什么所有方法都长一个样
看 `recordAiOutput`/`approve`/`reject`/`advance`,它们都是同一个骨架:
`拿路径 → 读 spec → 调纯状态机算新状态 → persist(写盘 + emit)`。
`persist` 是所有变更的**唯一收口**,保证"写盘"和"发事件"永远成对出现——
这就是不变量 #2 在代码里的落地点。

## 第 4 幕:三个真实的 Bug(最值钱的部分)

调试才是真正学到东西的地方。这三个坑都很典型。

### Bug 1 —— 不可变更新改错了对象(StageMachine)
**现象**:单元测试里 `gateHistory` 永远是空数组,明明调用了 approve/reject。
**根因**:`mutateStage` 里 `structuredClone` 出了副本 `next`,但 `transitionGate` 往
history push 时,用的是闭包捕获的**原始 spec**,不是 `next`。于是记录全落到了被丢弃的
原对象上,返回的副本里 history 是空的。
**修复**:让回调签名显式带上 `next`(`fn: (next, stage) => void`),强制往副本里写。
**通用教训**:做不可变更新(深拷贝再改)时,**务必确认你写的是副本那一份**,
闭包很容易让你不小心碰到原值。

### Bug 2 —— npm 装不上(vitest 4 的 peer 依赖让 npm 崩溃)
**现象**:`npm install` 直接报 `Cannot read properties of null (reading 'edgesOut')`。
**根因**:vitest 4 的 peer dependency 图触发了当前 npm 版本的一个 bug。
**修复**:把 vitest 固定到 2.x、vite 固定到 5.x(稳定的组合)。
**通用教训**:**最新版不等于最合适**。工具链报出看不懂的内部错误时,先怀疑版本组合,
退回到已知稳定的版本,而不是硬刚。

### Bug 3 —— 跨进程看板不刷新(最深的坑)
**现象**:e2e 里,Claude(MCP 进程)写了 spec,但浏览器连着的 dashboard(另一个进程)
看板不更新。
**根因**:dashboard 的事件总线(EventBus)只能感知**自己进程内**的变更。Claude 在**另一个
进程**改了文件,dashboard 的 EventBus 根本不知道,自然不推给浏览器。
**修复**:加 `FileWatcher`,用 chokidar **监听仓库的 `.specflow` 目录**,外部进程一改文件
就重新读出来、重新 emit `spec.updated`,看板就"自愈"了。
**还踩了子坑**:一开始监听的是 `.specflow/specs/` 这个叶子目录,但它在第一个 spec 写入前
**根本不存在**,chokidar 监听一个不存在的目录就不触发;而且 macOS 上跨进程文件事件要开
`usePolling`(轮询)才稳。改成监听更上层的 `.specflow`、并开轮询,才解决。
**通用教训**:**"进程内的事件总线"和"跨进程的文件变更"是两回事**。多进程共享状态时,
文件监听是让各进程保持一致的常见手段;且注意监听目标要在监听开始时就存在。

### 顺带修的一个设计错误 —— 运行模式写反了
调 Bug 3 时发现:`index.ts` 原本**总是**启动 dashboard,只在没有 `--dashboard` 时才启 MCP。
这导致 MCP 进程也去抢占 dashboard 端口。正确模型应是:`--dashboard` = 只跑 dashboard;
默认(无参)= 只跑 MCP。两者作为**独立进程**共享文件。
**通用教训**:调一个 bug 时常会牵出旁边的设计瑕疵,一并修掉。

## 第 5 幕:需求中途变了 —— per-repo prompt

做到一半,你提出:团队有多个仓库、框架不同(Java/Maven、npm、微服务),所以**每个仓库
需要自己的一套阶段 prompt**。这印证了那份 SAP blueprint 里的核心话:
> "自动生成只是起点,不是终点;高质量的 AI 配置需要人工策展。"
> "结构是统一的(Claude 产出什么、人把什么关),但 prompt 的内容应该是你们自己的。"

**我们怎么应对中途变更?** 没有推翻重来,而是把模板层设计成**三级回落**:
1. `<repo>/.specflow/templates/{stage}.md`(该仓库人工策展过的)—— 最优先。
2. (Phase 2 才有)草稿版。
3. 内置的 blueprint 通用默认(带 `[占位符]`)—— 兜底。

并且特意把"子 agent 探查仓库→自动生成 prompt"做成一个**预留接口**
(`generateCuratedTemplate`,v1 里先抛错),这样 Phase 2 可以无缝接上,v1 又不被拖慢。
**通用教训**:面对"未来可能要做"的需求,留一个清晰的接口缝(seam),比现在就全做了更明智——
既不过度设计,又不堵死未来。

## 第 6 幕:界面与"看得见的正确"

后端全绿后才做前端(React + Joule 深色玻璃拟态)。做完**在真实浏览器里跑了一遍**:
加仓库、建 spec、点 Approve,看卡片是否实时在泳道间移动。
**通用教训**:类型检查和单元测试证明"代码正确",但证明不了"功能正确"。UI 一定要真跑一遍
golden path,截图确认,而不是看到测试绿就宣布完成。

一个小的 UX 迭代:你希望"Add repo"能弹原生 Finder 而不是手打路径。这里有个**浏览器硬限制**:
网页的文件选择框拿不到文件夹的真实绝对路径(安全沙箱)。所以我们把选择动作放到**后端 Node
进程**用 `osascript` 弹原生对话框。**通用教训**:遇到"前端做不到"时,先想清楚是不是平台的
硬限制,再决定把能力下沉到哪一层。

## 第 7 幕:验证的纪律

每完成一块,固定跑四件事:
```
npm run build        # 能编译
npm test             # 单元 + 集成全绿
npm run test:e2e     # 端到端全绿
npx tsc --noEmit     # 类型零报错
```
还专门写了一个**"stdout 纯净性"测试**:真的 spawn 一个进程、喂它 JSON-RPC、断言 stdout 里
**每一行都是合法 JSON-RPC**。这是用自动化测试把"不变量 #1"钉死——以后谁不小心往 stdout
打了日志,这个测试立刻变红。
**通用教训**:把你最怕被破坏的那条铁律,写成一个会报警的测试。

## 给"把它变成自己项目"的你的建议

1. **先改需求、再改代码**:动手前,把"数据模型挂在哪个粒度""哪些做哪些不做"这类不可逆决策
   用几个问题敲定。
2. **由内向外、先测核心**:最稳定的业务规则最先写、最先测;界面最后做。
3. **分层 + 单一事实源**:算/存/编排/transport 分开;规则只实现一次。
4. **让错误尽早爆发**:边界上用 zod 校验,坏数据当场失败。
5. **调试即学习**:每修一个 bug,写下"现象/根因/修复/通用教训"四段——就像本文第 4 幕。
   这些是比语法更难得的经验。
6. **留缝不过度**:未来功能留接口(seam),别现在就全做。
